## 审查对象

供任何接手或协作的 AI 阅读：需要评估、安装、维护或扩展本仓库的工程治理工作流时。

## 结论摘要

本仓库原先的设计理念合格，但只具备“规则目录骨架”，不具备可执行、可验证、可演进的闭环：没有实际规则和交付流程，没有机器校验，也没有项目可复制的 enforcement 模板。此次改造建立了最小闭环；它不是某个项目的现成 CI，也不应被误读为已经在任何业务仓库强制生效。

## 问题清单

| # | 步骤 | 谁做 | 产出 | 进入下一步的条件 |
|---|---|---|---|---|
| 1 | 读取基线 | 协作 AI | 相关规则、工具说明和本审计结论 | 知道目标项目的语言、目录和验证命令 |
| 2 | 项目化映射 | 主 agent 与人 | 完整 `AGENTS.md`、语言/文档白名单、质量命令 | 每项设置都来自项目事实，而非模板猜测 |
| 3 | 安装并触发门禁 | 主 agent | hook/CI 配置和一次真实触发结果 | 文件超限和目录外文档均能被检测 |
| 4 | 日常执行与复盘 | 主 agent、审查 agent 与人 | 有证据的交付记录、窄范围改进 | 新规则由重复问题或风险证据支持 |

### 停止条件（gate）

- 目标项目的测试命令、文档允许目录或 CI 平台未知时，停止安装强制配置，先做只读调研或询问负责人。
- 未在真实项目中触发过 hook/CI 时，停止将其描述为“已生效”。
- 某项规则无法明确其误报处理或豁免记录方式时，保留为文档建议，不升级为阻断门禁。

## 建议的处置顺序

- 三项可判定基线规则：文件规模、文档治理、变更证据。
- 一个带人工 gate、独立审查和证据交付的变更流程。
- 一个项目 `AGENTS.md` 模板和一个可配置 PowerShell 治理检查脚本。
- Codex 落地说明，明确 rules、skills、子 agent、hooks 与 CI 的职责边界。
- 一个无第三方依赖的 playbook 结构校验器：`python tools/validate_playbook.py`。

### 协作 AI 的工作协议

1. 先阅读 `README.md`、本文件和与任务相关的单条规则；不要把整个 playbook 当成业务项目规则直接照搬。
2. 每条新增规则必须回答：触发条件是什么、能否机械判定、在哪一层执行、如何验证、误报如何处理。
3. “指令”与“强制”必须分开报告：AGENTS/rule 是引导，hook 是本机门禁，CI 才是共享且难以绕过的门禁。
4. 只将互不重叠且可验证的工作委派给子 agent；所有实现和验证的最终责任归主 agent。
5. 规则变更必须以真实失败、重复摩擦或新风险为证据。不要把单次偏好升级为所有项目的硬约束。
6. 修改后运行 `python tools/validate_playbook.py`；如果修改了脚本，还要运行脚本的安全、可重复测试并报告实际结果。

### 仍待项目化的事项

- 选择每个项目的源码后缀、生成目录排除项、文档白名单和质量命令。
- 将 `check-governance.ps1` 接入该项目的 hook 与 CI，并在真实 diff 上验证。
- 依据项目技术栈创建少量、触发条件明确的 skills；不要预先创建泛化的“全栈专家”。
- 以真实工作记录校准 800 行阈值和文档白名单；必要时允许有记录的豁免。

### 验证方式

执行：

```powershell
Set-Location D:\APP\AI\agent-playbook
python tools/validate_playbook.py
```

通过仅表示 playbook 的 Markdown 结构完整；不表示模板已在任何项目安装、hook 已加载，或项目测试已经通过。

### 对应工具实现

| 工具 | 怎么落地 |
|---|---|
| Codex | 见 `tools/codex.md`；在项目内放 `AGENTS.md`、skills、可执行脚本和 CI。 |
| Cursor / Claude Code | 复用同一规则与脚本，但按各工具的项目规则和 hook 位置映射；不得把配置路径互相混用。 |
