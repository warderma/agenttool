## 适用场景

适用于会修改代码、配置、依赖、工作流或受控文档的任务。单纯问答和只读检索不需要完整流程。

## 步骤

| # | 步骤 | 谁做 | 产出 | 进入下一步的条件 |
|---|---|---|---|---|
| 1 | 只读调研 | 主 agent；必要时委派只读调研 agent | 涉及文件、现状、约束、测试命令、未知项 | 需求和现状没有未经标注的假设 |
| 2 | 最小变更计划 | 主 agent | 文件清单、接口影响、验证方案、是否需文档 | 范围可描述且没有高风险未决项 |
| 3 | 人工 gate | 人 | 对范围、架构取舍、目录外文档、外部副作用作出决定 | 已明确批准，或任务本身已包含足够明确授权 |
| 4 | 实现 | 实现 agent 或主 agent | 最小代码/配置改动和对应测试 | 不越过批准范围，文件所有权不冲突 |
| 5 | 质量验证 | 主 agent | 格式、lint、类型、测试、治理脚本的真实输出 | 所有适用检查通过，或失败已修复/获得接受 |
| 6 | 独立审查 | 只读 review agent | 按严重度的发现、证据和遗漏检查 | 高严重度问题已修复或被明确接受 |
| 7 | 交付 | 主 agent | 改动、验证、风险和后续项摘要 | 结论由证据支持 |

## 停止条件（gate）

- 需求导致公开 API、数据模型、安全边界、部署或依赖升级时，在实现前等待确认。
- 需要删除数据、大规模迁移、对外通信、提交/推送/部署时，在动作前等待单独确认。
- 计划外新增文档、跨越文件所有权或验证失败时，停止扩展范围，先解决或升级风险。

## 反例

- 未调研测试和现有约定就直接修改二十个文件。
- 两个 agent 同时写同一模块，之后按“最后写入者”为准。
- 将 review agent 的“未发现问题”当成测试通过。

## 验证方式

交付前检查每一步是否有对应产物；运行目标项目的质量命令和 `check-governance.ps1`。审查输出必须是独立上下文生成，且附带检查范围。

## 对应工具实现

| 工具 | 怎么落地 |
|---|---|
| Codex | 用根目录 `AGENTS.md` 绑定规则；用 `.codex/skills/` 存可复用流程；用独立 subagent 做调研和审查；用 `.codex/hooks.json` 与 CI 执行确定性检查。 |
| Cursor | 用 `.cursor/rules/` 和 `.cursor/agents/` 绑定规则与角色；其 hook 配置必须使用 Cursor 专用模板，不能复用 Codex 模板。 |
| Claude Code | 将同样的约束映射到其项目说明、skills 与 hooks；每次映射后运行同一治理脚本。 |
