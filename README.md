# Agent Playbook

> **一句话**：这里放「怎么指挥 AI 写代码」的规则与方法——**不是**工具安装目录，也不是项目代码。

上级目录 `D:\APP\AI` 下是各种 AI 工具的安装位置（codex / cursor / deepseek …）。
本目录只关心一件事：**同样的约束和流程，怎么跨工具复用、怎么真正生效。**

---

## 0. 给接手 AI 的读取顺序

如果你是新接手这个目录的 AI，**按这个顺序来，不要跳**：

1. 读完本文件（尤其第 3、5、6 节）
2. 打开 `rules/` 的索引，**只读和当前任务相关的那几条**
3. 动手改任何文件前，读第 5 节「维护约定」
4. 改完后必须运行 `python tools/validate_playbook.py`；更新 frontmatter 的 `last_verified`，并在第 8 节变更记录里加一行

**不要做的事**：不要批量重写已有规则、不要引入新的目录层级、不要在没有验证方式的情况下写规则。

---

## 1. 这个目录是什么 / 不是什么

| 是 | 不是 |
|---|---|
| 跨工具复用的**约束**（源文件行数、文档目录、命名） | 工具安装包（在上级目录） |
| 端到端**流程**（需求 → 计划 → 实现 → 审查） | 某个具体项目的业务代码 |
| 可复制的**模板**（AGENTS.md、prompt、检查脚本） | 一次性的调试笔记 |
| 每个工具的**落地方式**（Codex 怎么写、Cursor 怎么配） | 教程搬运 / 链接收藏夹 |

判断标准：**换一个项目还能用吗？** 能，就属于这里；不能，属于那个项目自己的 `.codex/` 或 `AGENTS.md`。

## 2. 目录结构

```
agent-playbook/
├── README.md          ← 本文件：地图 + 约定 + 变更记录（索引文件，例外于 frontmatter）
├── rules/             单个约束，一条一个文件
├── workflows/         端到端流程，一个流程一个文件
├── templates/         可直接复制到项目里的模板文件
├── tools/             同一套规则在不同工具上的落地方式 + 校验器
└── reviews/           同行审查记录；只记录证据、问题与处置建议
```

| 目录 | 放什么 | 命名 |
|---|---|---|
| `rules/` | “单文件不超过 800 行”“禁止新建散落文档”这类**单条可判定约束** | `rule-<短横线描述>.md` |
| `workflows/` | “需求→计划→TDD→审查→PR”这类**多步骤流程** | `wf-<流程名>.md` |
| `templates/` | `AGENTS.md`、`pre-commit`、`check.sh` 等**能直接拷走的文件** | 与目标文件同名，加 `.tpl` 后缀 |
| `tools/` | 同一套东西在 Codex / Cursor / Claude Code 上**分别怎么配** | `<工具名>.md` |

## 3. 文件格式约定（所有文件必须遵守）

除 `README.md` 和各目录的 `_TEMPLATE.md` 外，每个治理 Markdown 文件**必须**以 frontmatter 开头：

```yaml
---
id: rule-file-size
type: rule            # rule | workflow | template | tool
scope: global         # global | project
applies_to: [codex, cursor, claude-code]
enforcement: hook     # doc | hook | ci
enforcement_status: template-only # planned | template-only | installed | verified
last_verified: 2026-10-21
---
```

规则正文固定四段；工作流、工具和模板使用各自模板的固定段落：

```markdown
## 适用场景
什么时候该用这条（越具体越好，能写成 if 条件）

## 规则
用祈使句，一句话一条；能被程序判定

## 反例
具体到代码/文件名，不要抽象描述

## 验证方式
怎么证明它生效了：跑什么命令、看什么输出
```

### `enforcement` 字段最重要

它决定这条规则**有多硬**：

| 值 | 含义 | 模型会不会守 |
|---|---|---|
| `doc` | 只写在 AGENTS.md 里 | **经常忘** |
| `hook` | 编辑/提交时脚本检查 | 大部分会改 |
| `ci` | 提交或流水线直接 fail | 绕不过 |

**任何 `enforcement: doc` 的规则，都应该在 `## 验证方式` 里写明“为什么还没上脚本”。**

`enforcement` 表示目标执行机制，`enforcement_status` 表示该机制的实际状态；两者不能混用。任何 `hook` 或 `ci` 机制在真实项目触发成功前都必须标为 `template-only` 或 `installed`，不得写成 `verified`。

### 规则、执行与证据的边界

- `rules/` 只声明不变量；不复制粘贴执行细节。
- `workflows/` 定义进入条件、产物、人工 gate 和退出条件。
- `templates/` 提供可复制的项目配置与脚本。
- `tools/` 说明特定产品的安装/触发位置；`tools/validate_playbook.py` 只验证本 playbook 的结构，不会替代项目 CI。
- 任何“已验证”都必须有可重复执行的命令或实际产物，不能以 AI 的口头结论代替。

---

## 4. 三条硬性写作规则

1. **规则必须可判定**。❌“代码要优雅” ✅“函数不超过 50 行”。
2. **必须写验证方式**。没有验证方式的规则是愿望，不是规则。
3. **必须标 enforcement 强度**。默认 `doc`，能上 `hook` 的尽快上。

## 5. 维护约定

| 操作 | 做法 |
|---|---|
| **新增** | 复制对应目录的 `_TEMPLATE.md`，改 frontmatter 和正文；同步添加可运行验证或明确说明为何暂不能自动验证 |
| **修改** | 改正文 + 更新 `last_verified` + 第 8 节加一行 |
| **废弃** | 移到 `archive/`（保留路径），**不要直接删** |
| **冲突** | 两条规则打架时，以 `enforcement` 强的那条为准，并合并另一条 |
| **改工具配置** | 只改 `tools/` 下的文件，不把工具安装信息写进来 |

**禁止**：
- 写不可验证的规则
- 把项目专用的东西放进来（应该进那个项目的 `AGENTS.md`）
- 一次改超过 3 个治理文件而不说明原因。初始化、迁移和跨文件一致性改造可例外，但必须在变更记录说明范围和原因。

## 6. 最小执行闭环

每个项目只需要从以下最小集开始；不要先堆积十几个角色和提示词。

1. 从 `templates/AGENTS.md.tpl` 生成项目根目录的 `AGENTS.md`，并替换占位符。
2. 从 `templates/codex-hooks.json.tpl` 和 `templates/check-governance.ps1.tpl` 安装项目 hook；在 Codex 的 Hooks 页面审阅并信任它，再在本地触发一次。
3. 将项目实际的 `lint`、类型检查和测试命令填入 `AGENTS.md` 中的质量门禁。
4. 任务按 `workflows/wf-change-delivery.md` 执行：调研、计划、实现、验证、独立审查、交付。
5. 每月或每完成 5 个有代表性的任务，依据失败证据调整一条规则或一个脚本；不要把一次偶发问题变成全局禁令。

### Delegation protocol

- 只将可独立验证且输入边界明确的工作交给子 agent，例如只读调研、测试设计、独立审查。
- 子 agent 默认只读；需要改文件时，必须分配互不重叠的文件所有权。
- 子 agent 的交付必须包含：结论、证据（路径/命令/输出）、风险、未验证项；主 agent 负责整合和最终验收。
- 没有独立性、预计只需数分钟或需要同一批文件的任务，不委派。
